# 加速度前馈：从视觉参考接到最终力矩

[移植步骤](firmware_porting.md) · [控制模型](control_design.md) · [2026-10-16 整机核查](porting_review_20261016.md) · [实机图册](hardware_debug_screenshots_20261007.md)

公开 C 内核已经支持加速度前馈：把目标加速度传入 `YawReference.acceleration_rad_s2`，核心将 `J * acceleration_rad_s2` 加入总力矩，再统一处理限幅、变化率和抗饱和。宿主无需再在控制器输出后补加一次。

这份说明依据新整机快照中暴露的接线问题补充。此前截图中用户标注的“加速度前馈开启”，与本次源码归档中被注释的分支分别保留；没有把两个版本当作同一轮实验。

## 三种信号分别接在哪里

| 信号 | 入口与作用 | 关闭或接错时的影响 |
| --- | --- | --- |
| 实测角速度 `ω` | `YawFeedback.velocity_rad_s`，参与 `Kω(ωr−ω)` | 不能为了关闭加速度前馈而将实测速度置零，那会同时移除速度反馈 |
| 目标角速度 `ωr` | `YawReference.velocity_rad_s`，参与速度误差及名义阻尼/摩擦前馈 | 跟踪运动参考时不能先赋值又无条件清零 |
| 目标角加速度 `αr` | `YawReference.acceleration_rad_s2`，产生 `Jαr` | 单独比较加速度前馈时，只把这一项设为零 |

目标的角度、速度、加速度应来自同一轨迹、同一坐标和一致时间；单位为 rad、rad/s、rad/s²。`Q=diag(qθ,qω)` 设计出的 `Kω` 不等于目标速度已接入，也不等于加速度前馈已开启。实测角速度须是控制角度的导数，不能直接假设任一机体系 gyro 分量都适用。

视觉协议若使用 rad，直接交给公开接口；旧类接口若接收度，只在进入那个接口时转换。遥控、自瞄、键鼠入口应共用同一单位映射。不要在一个分支乘 `180/π`、另一个分支原样传入相同字段。

## 最小接入方式

保留已有任务、模式管理和 CAN 发送者。下面片段放在已有控制周期内；`source_reference` 是宿主已经完成单位转换、有限数检查、轨迹约束和来源年龄计算的一致快照：

```cpp
YawReference reference = source_reference; // rad / rad/s / rad/s² / s
if (!acceleration_ff_enabled) {
    reference.acceleration_rad_s2 = 0.0f;
}
// feedback 始终携带真实角速度；pose 使用机械关节角和重力角。
const YawStatus status = gimbal_controller_step(
    &axis, &feedback, &reference, &pose, actual_dt_s, &output);
if (status != YAW_OK && status != YAW_WARMUP) {
    invalidate_pending_axis_command(); // 宿主实现
    request_host_stop(status);         // 宿主实现
    return;
}
publish_to_existing_group_owner(output.control.torque_nm); // 宿主实现
```

每轴各持有一个 `GimbalController` 和对应配置。宿主自定义重力曲线改用 [外部重力入口](firmware_porting.md#3-迁移宿主已有的重力曲线)，其余顺序相同。`YAW_WARMUP` 的输出为零，不能在这一步再加重力或加速度项。

`output.control.feedforward_nm` 包含惯性、阻尼、摩擦及已知负载，**不是单独的加速度前馈力矩**。要看 `Jαr`，另记录本轮实际 `J` 与处理后的 `αr`；要核对电机最终收到什么，还应记录限幅后的 `torque_nm` 和所属 CAN 槽位。

现有 [C++17 宿主测试](../tests/cmake_port/main.cpp) 演示同一接口下开启/关闭加速度项，保持目标速度、来源年龄和重力不变，并分别验证 GM6020、DM4310 的链接路径。

## 加速度从哪里来、如何约束

优先使用轨迹生成器或视觉预测器提供的速度和加速度。只有角度目标时，宿主需要先生成受约束的轨迹；对带跳变的角度包连做两次数值差分，会把目标切换或丢包变成很大的前馈脉冲。

公开核心拒绝 NaN/Inf 和过期参考，并限制最终力矩；它没有独立的目标加速度上限。宿主应在生成参考时设置与机构和力矩预算一致的速度、加速度约束，保留约束触发标志。仅夹住 `αr` 可以限制惯性项，却不能使原本不一致的 `θr/ωr/αr` 自动变成可行轨迹。若必须滤波，记录滤波状态和引入的延迟，并在模式切换时同步；本库的 `velocity_error_filter_tau_s` 滤的是**速度误差**，不会滤目标加速度。

Pitch 到边界时，位置、向外速度和向外加速度需要一起处理。公开适配层检查机械角、映射后的目标位置和目标关节速度；**它没有底座角加速度输入，不能完整推断目标关节加速度**。宿主轨迹层应完成相应坐标关系和限位处的导数约束。静止底座下，可在目标被夹到上/下边界时去掉继续向外的速度与加速度；运动底座不能直接把世界角导数当成关节角导数。

## 与 ESO、周期和复位的衔接

```text
同一时刻的 θr / ωr / αr
           ↓
Jαr + Bωr + 摩擦 + 重力 + LQR反馈 + 积分 + ESO补偿
           ↓
总幅值限制 → 变化率限制 → 再硬限幅 → 原有 CAN 所有者
           ↓
保存最终命令，供下一周期 ESO 预测使用
```

ESO 默认使用上一周期的最终总力矩；加速度前馈已经在其中。不要从这个命令里再扣一次 `Jαr`，也不要把它当成外界扰动或重力负载。只有确有上一完整控制区间平均执行力矩时才设置 `applied_torque_valid`，本帧命令不能替代这个测量。

`actual_dt_s` 是真实调用间隔，参考 `age_s` 则从原始数据来源时刻计算。控制任务重复读同一个包，不能把包年龄重置为零。滤波重采样或名义 1/2 ms 常量也不能使陈旧数据变新；模式切换时需要同步轨迹、滤波器、积分、观测器及时间历史，随后按原有显式复位流程暖机。

二阶角速度 NLESO 与本库三阶位置 LESO 的状态、输入位置和参数含义不同。迁移应核对状态方程及扰动的物理单位，不能把某个 `β` 或非线性参数直接填进本库 `eso_bandwidth_rad_s`。

## 可运行的接线回归

```bash
cmake -S . -B build/feedforward-check -DCMAKE_BUILD_TYPE=Release
cmake --build build/feedforward-check --parallel
ctest --test-dir build/feedforward-check -R 'yaw_controller|multiaxis' -V
python3 -m unittest discover -s tests -p 'test_cmake_port.py'
```

这些测试调用真实公开 C 实现，无需私有 ZIP：

| 回归 | 检查什么 |
| --- | --- |
| 1 ms / 2 ms 加速度开关对照 | 同一理想正弦轨迹，只切换 `Jαr`，保留实测速度反馈和目标速度；独立 ZOH 被控对象计算误差 |
| 前馈与 ESO 输入历史 | 无扰动、交替加减速和抖动周期下，用上一总命令驱动模型；ESO 残余扰动应接近零 |
| 前馈触发饱和 | 零位置误差下，过大的加速度前馈仍经过总限幅、变化率与积分反算；反向、过期参考、锁存和复位均检查 |
| 轴间隔离 | 只激励 Yaw 时 Pitch 的积分与力矩为零；再反向检查，复位/故障也不串轴 |
| C++17 宿主 | 加速度开关确实改变前馈分项，目标速度和来源年龄保持，两个电机接入目标均可运行 |

正弦测试采用 `J=0.039`、`B=0.30`、`Kθ=10`、`Kω=1`，幅值 0.08 rad、2 Hz，Ki 和 ESO 关闭；运行 4 s，统计 0.5–4 s。该组刻意避免饱和，无噪声和额外执行器滞后，用来发现前馈接线回归。限幅行为由另一组测试覆盖。打印的 RMSE 是合成结果，不是 GM6020 实机指标，也不替代已有含失配、噪声与延迟的性能验收。

## 下一轮实机记录

先固定 Q/R、实际 K、Ki、ESO、轨迹、负载、滤波和时间条件，只切换加速度前馈，每组至少保留三次完整运行。之后再单独比较 ESO 补偿开关；不要同时换 Q、增益、前馈和观测器后把收益归给其中一项。

日志至少包含原始与处理后的 `θr/ωr/αr`、反馈角与速度、包源戳/年龄、实际 dt、分项力矩、限幅标志、最终命令和模式事件。用 [移植记录模板](../examples/porting_record_template.md) 同时保存源码/固件哈希和逐轴实际开启路径；视觉曲线、内存变量和最终 CAN 命令应能对得上。
